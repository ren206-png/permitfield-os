## §2. Existing canonical records this module must reuse, not duplicate

### 2.1 Organizations / tenancy

`organizations` (`supabase/migrations/20260806000002_organizations_and_members.sql:5-9`): `id`,
`name`, `created_at`. This is the tenant boundary for the entire app; every new table this module
adds must carry `org_id` and be RLS-scoped the same way.

### 2.2 Roles

`org_role` enum, defined `20260806000002...sql:11` as `('owner', 'member')`, additively extended at
`20260806000018_lifecycle_rbac_roles_and_audit_log.sql:26-33` to 10 total values: `owner`, `member`,
`platform_admin`, `org_owner`, `permit_manager`, `permit_coordinator`, `document_reviewer`,
`applicant_contractor`, `client_user`, `auditor_readonly`. `org_members.role` cannot be
`client_user` (`20260806000029_org_members_role_not_client_user.sql:35-37`).

**Note the naming quirk directly relevant to this module**: both `owner` (original, unused in
practice per later roles) and `org_owner` (added later, the role actually used for org ownership)
exist simultaneously. There is **no `billing`, `staff`, or `read-only` role** in this enum — the
master prompt's role table (owner/admin/billing/staff/read-only) does not map onto this enum
1:1. The closest matches are `org_owner` (owner), `permit_manager`/`platform_admin` (admin-ish),
nothing for `billing` specifically, several roles that could serve as `staff` depending on how this
module scopes issuance rights, and `auditor_readonly` (read-only). This mapping is not obvious and
is listed as a blocking question in §I.

A parallel, more granular TypeScript authorization module exists at `lib/authz/index.ts`: a `Role`
type (10 values, lines 32-42), an `Action` type (`create | read | update | archive`, line 52), a
`Resource` type (17 resources, lines 107-124), and a table-driven `can(role, action, resource): boolean`
(lines 473-476) that fails closed for unmodeled pairs. **Its own header comment (lines 6-24) states
it is not wired into any real route today** — actual enforcement in production is RLS
(`is_org_member()`/`is_org_owner()`), not `can()`. Only one call site exists
(`app/(app)/projects/new/actions.ts`, per `lib/authz/index.ts:65`). Any authorization design for
this module that assumes `can()` is actively enforced would be wrong; it is foundation/aspirational
code as of this pass.

### 2.3 Customer / job model

**No `customer`/`customers` table exists.** The only "customer" in the schema is
`org_subscriptions.stripe_customer_id` (Stripe's own customer ID for the SaaS subscription — not a
domain entity). **No `job`/`jobs` table exists** (`ai_jobs` is an unrelated AI-pipeline ledger, see
§2.6).

What *does* exist, and is the correct reuse target:

- **`clients`** (`20260806000019_lifecycle_intake_properties_clients_taxonomies.sql:87-98`): `id`,
  `org_id`, `name`, `email`, `phone`, `notes`, `archived_at`, `created_at`, `updated_at`. Explicitly
  documented in that migration as the org's own customer/CRM record (a homeowner or business who
  hired the org's contractor) — this is the canonical "customer" entity a quote/invoice should
  reference.
- **`projects`** (same migration, lines 143-165): `id`, `org_id`, `client_id`, `property_id`,
  `contractor_id`, `taxonomy_id`, `title`, `description`, `property_owner_name`, `applicant_name`,
  `status` (`project_status` enum: `draft/active/on_hold/completed/archived`), `archived_at`,
  timestamps. This is the canonical "job" entity — `permit_applications.project_id` links a permit
  filing to a project (`20260806000022_permit_status_machine.sql:150,158-160`), which is exactly the
  "a permit application may exist for a job, or may not" relationship the master prompt describes.
- **`properties`** (same migration, lines 109-124): the physical address/site entity.

### 2.4 Permit lifecycle (must remain independent, per the master prompt's own instruction)

`permit_applications` (`20260806000006_applications_and_documents.sql:17-31`, extended by
`20260806000022...sql:148-153`) carries two parallel status machines: `application_status` (AI
pipeline progress: draft→...→submitted) and `permit_status_enum` (16-value real-world lifecycle:
`intake` through `closed`, `20260806000022...sql:90-107`), the latter only mutable through a
SECURITY DEFINER RPC (`transition_permit_status()`) with direct column UPDATE revoked from
`authenticated`. A quote/invoice must reference `projects`/`clients`, optionally
`permit_applications`, and must never infer permission to start work, or automatically change permit
state, from quote/invoice/payment events — this is directly enforceable today because permit-status
mutation is already locked down to one RPC that this module has no reason to call.

### 2.5 Documents / storage

Two private Supabase Storage buckets, 25MB cap each (`20260806000013_storage_buckets.sql:5-9`):
`permitfield-uploads`, `permitfield-generated`. Path convention
`${orgId}/${applicationId}/${sha256}-${filename}`, tenant-scoped via
`storage.foldername(name)[1]::uuid` + `is_org_member()` RLS policies (same migration, lines 19-31,
45-50). `application_documents` (`20260806000006...sql:35-49`, extended
`20260806000024_lifecycle_documents_revisions.sql:81-102`) is the metadata table, with
`document_revisions` for append-only revision history and no hard DELETE (replaced by an
`archive_application_document()` RPC). **No generic `documents` table exists** — everything routes
through this application-scoped pair. A quote/invoice PDF would need either a new bucket
(`permitfield-quotes-payments` or similar, following the same path-and-RLS convention) or a
generalization of this pattern — the existing one is application-scoped by construction
(`${applicationId}` in the path, and RLS assumes a `permit_applications` join in one variant), so it
does not extend cleanly to a job that has no permit application. This is a real design decision, not
a copy-paste reuse.

### 2.6 Payments / subscriptions (existing — SaaS billing only)

`org_subscriptions` (`20260806000040_org_subscriptions.sql:23-46`): one row per org
(`org_id uuid unique`), `stripe_customer_id`, `stripe_subscription_id`, `tier`
(`org_subscription_tier`: starter/pro/enterprise), `status` (`org_subscription_status`:
trialing/active/past_due/canceled), `current_period_end`, `trial_ends_at`,
`stripe_event_created_at` (added `20260806000042...sql:15`, an out-of-order-webhook guard).
`authenticated` has **SELECT only** — no INSERT/UPDATE/DELETE grant ever existed for that role
(`20260806000040...sql:76`), and migration 44 (unmerged, PR #17) adds an explicit
`revoke insert, update, delete on org_subscriptions from authenticated;`
(`20260806000044_org_subscriptions_revoke_authenticated_write.sql:42`) closing a gap that had
appeared via a different migration path — confirmed fixed and CI-verified as of this pass, but not
yet on `main`. `service_role` has SELECT/INSERT/UPDATE (`20260806000040...sql:83`). Writers: the
`create_organization_with_owner()` SECURITY DEFINER RPC (initial row) and the Stripe webhook
handler using a `service_role` client.

**Stripe webhook handler**: `app/api/webhooks/stripe/route.ts` — `POST`, gated by
`isBillingEnabled()`, verifies signature over raw body text. **Core billing logic**:
`lib/billing/subscriptions.ts` — the *only* module allowed to import the `stripe` package (ESLint
`no-restricted-imports` rule, per its own header comment). Handles `checkout.session.completed`,
`customer.subscription.updated`, `customer.subscription.deleted`, `invoice.payment_failed` — this
event list has nothing to do with a contractor's own connected-account payments; it exists solely to
keep `org_subscriptions` in sync with PermitField's own SaaS billing. **This is the flow the master
prompt calls "flow A" and says must never be conflated with "flow B" (contractor's customer paying
for contracted work)** — confirmed: there is currently no flow B in this codebase at all. No
`invoices`, `payments`, `quotes`, or line-item table exists anywhere in the repo today. Phase C's
Stripe Connect work would be a second, structurally separate Stripe integration
(likely also needing its own `no-restricted-imports`-style guard so flow-A and flow-B code can't
accidentally cross-import).

`lib/billing/tiers.ts`: `BillingTierId = 'starter' | 'pro' | 'enterprise'`, `BILLING_TIERS` record
with `priceCents`, `features: readonly Entitlement[]`, `limits`. `lib/entitlements/index.ts`:
`can(orgId, entitlement): Promise<boolean>` and `limit(orgId, key): Promise<number>`, DB-backed when
`PERMITFIELD_FF_BILLING` is on, fails closed to zero features on any DB error
(`lib/entitlements/index.ts:120-125`). See §3.2 for the entitlement-key convention this module
should follow.

## §3. Conventions to reuse (not reinvent)

### 3.1 Feature flags

`lib/flags.ts` — single private helper `isEnabled(envVarName)` (`lib/flags.ts:12-14`):
`return process.env[envVarName] === 'true';` — strict equality to the literal string, so anything
else (unset, `"false"`, `"0"`, a typo) resolves OFF. 18 exported flags follow the pattern
`export function is<Capability>Enabled() { return isEnabled('PERMITFIELD_FF_<CAPABILITY>'); }`
(e.g. `isBillingEnabled` → `PERMITFIELD_FF_BILLING`, `isClientPortalEnabled` →
`PERMITFIELD_FF_CLIENT_PORTAL`). One documented exception: `isMarketingV2Enabled` uses
`NEXT_PUBLIC_MARKETING_V2` because that flag must be readable from a client component. **A new flag
for this module should be `PERMITFIELD_FF_QUOTES_PAYMENTS`** (server-only, matching every flag
except the one documented client-readable exception), with sub-phase flags following the same
pattern if Phase B/C need independent kill switches (e.g. `PERMITFIELD_FF_QUOTES_PAYMENTS_ONLINE`
for Phase C, to satisfy the master prompt's "never block the offline pilot on the online
integration" requirement with a real, independently-flippable flag rather than a shared one).

### 3.2 Entitlements

`lib/billing/tiers.ts:20-26` defines `Entitlement` as a plain string-literal union, dot-namespaced:
`'projects.create' | 'readiness.checker' | 'readiness.override' | 'jurisdiction.requirements' |
'analytics' | 'ai'`. Pattern: `<domain>.<action>`, distinct in style from the flags' SCREAMING_SNAKE
convention — `lib/flags.ts` itself calls out this divergence as deliberate. A new entitlement for
gated Quotes & Payments capability (e.g. per-province issuance, online payments) should follow this
same `quotes.issue` / `payments.online` style, added to `BILLING_TIERS`'s per-tier feature list, not
invented as a new naming scheme.

### 3.3 Audit log

`audit_logs` (`20260806000018...sql:52-65`): `org_id`, `actor_user_id`, `actor_role` (nullable as of
`20260806000030_audit_logs_external_actor.sql`), `action`, `entity_type`, `entity_id`,
`before_summary`/`after_summary` jsonb, `ip`, `user_agent`, `occurred_at`. Migration 30 widens this
for external (client-portal, non-authenticated) actors: `external_actor_id`, `external_actor_label`,
with a CHECK requiring exactly one of {internal actor pair, external actor id}. Append-only —
`forbid_update_delete()` trigger blocks UPDATE/DELETE for every role including `service_role`.
Canonical write helper: `writeAuditLog(supabase, entry)` at `lib/audit/log.ts:74-105`, never throws
(`{data, error}` return), two legal shapes matching the SQL CHECK. **Not universally used** — two
SECURITY DEFINER SQL functions write to `audit_logs` directly, bypassing the TS helper
(noted in `20260806000030...sql:63-67`). A Quotes & Payments module should use `writeAuditLog()` for
every issuance/void/payment-record/refund/tax-override/role-change action the master prompt's §9
adversarial checks care about, and should follow the external-actor shape for any action taken via a
customer-facing link (quote acceptance, payment) the same way `lib/bridge/client-portal.ts:970-980`
does for client document uploads.

### 3.4 SQL test suite

18 files, `supabase/tests/*.test.sql`. Pattern (confirmed by reading `org_subscriptions.test.sql`
and `audit_logs.test.sql` in full): whole file wrapped `begin; ... rollback;`; role/identity
simulation via `set local role authenticated;` + `set local request.jwt.claims = '{"sub":"<uuid>",
"role":"authenticated"}';`, always followed by `reset role;`; assertions as
`do $$ begin <action>; raise exception 'FAIL: ...'; exception when <specific_sqlstate> then raise
notice 'PASS: ...'; end $$;` blocks — **the specific-SQLSTATE discipline matters**: a recent PR
(#16, unmerged) fixed exactly the failure mode of catching `insufficient_privilege or others`, which
silently masks a test by also catching the block's own `raise exception 'FAIL...'` line. New tests
for this module must match precise SQLSTATEs, not catch-alls. Coverage order convention: positive
path → RLS positive (own-org read) → RLS negative (cross-org denied) → privilege-boundary
(`authenticated` write attempt expects `insufficient_privilege`) → `service_role` write +
cross-tenant visibility. Run via `npm run test:sql` (main project) /
`npm run test:sql:client-portal` (second project), both wired into CI (§7).

### 3.5 Money (already exists — real head start on §4 of the master prompt)

`lib/money/cents.ts` (on `main`, unrelated to any open PR) is a deterministic, float-free
currency-string↔integer-cents module: `parseCurrencyToCents(raw): bigint | null` (BigInt arithmetic
only, no `Number()`/`parseFloat` anywhere in the file, returns `null` — never zero — when
unparseable), `centsToSafeNumber(cents): number` (guards against exceeding
`Number.MAX_SAFE_INTEGER`, since `permit_applications.estimated_job_value_cents` crosses the
JS/Postgres `bigint`↔`number` boundary), `centsToDollarsString(cents): string` (BigInt + string
manipulation, explicitly no `toFixed()`/`toLocaleString()`/`Intl.NumberFormat`). This satisfies the
master prompt's "integer CAD cents, never binary floating-point for money" requirement for
single-value conversion, but is **not** a full line-item calculation engine — it has no concept of
quantities, discounts, tax computation, or rounding-order across multiple line items. A shared,
tested calculation engine (§4 of the master prompt) is new work; `lib/money/cents.ts` is the correct
foundation to build it on (same file, or a new `lib/money/quote-calculator.ts` sibling), not a
reason to consider §4 already done.

`.github/workflows/ci.yml`: two independent jobs on every push/PR to any branch. `build-and-test`
(fast: lint, build, `npm test`). `sql-tests` (Docker-backed: `supabase start` → `supabase db reset`

## §4. Client-facing access-token model — the decision the master prompt requires

The master prompt requires an explicit decision on whether customer financial documents (quote/
invoice links) ride the existing token system, extend it, or justify a separate one. Findings:

The existing system lives entirely in the **second Supabase project**
(`supabase-client-portal/`), behind one gateway module, `lib/bridge/client-portal.ts` (1268 lines —
the only file in the repo permitted to import the client-portal service client, enforced via an
ESLint `no-restricted-imports` rule). Schema
(`supabase-client-portal/supabase/migrations/20260814000001_client_portal_token_schema.sql`):

- `client_access_tokens` (lines 20-70): `token_hash` (unique, sha256 hex, **raw token never
  stored**), `recipient_email`/`recipient_email_display` (normalized vs. as-typed, tied by CHECK),
  `application_id`/`org_id` (bare cross-project pointers, not FKs — by design, see the migration's
  own comment), `status` (`active/expired/revoked/superseded`), `expires_at`,
  `revoked_at`/`revoked_by_*`. A partial unique index enforces at most one *active* token per
  `(recipient_email, application_id)` — this is the closest thing to "recipient-keyed" in the repo;
  the literal term "recipient-keyed" does not appear anywhere (zero grep hits).
- `token_lifecycle_events` and `client_access_log`: append-only (same `forbid_update_delete()`
  trigger pattern, enforced even against `service_role`).
- **No RLS policy exists for `authenticated`/`anon` on any of these three tables** — only
  `service_role` ever touches project 2, because project 2 has no end-user Supabase Auth session at
  all.

Generation/validation, all in `lib/bridge/client-portal.ts`: `generateRawToken()` (256-bit,
`randomBytes(32).toString('base64url')`), `hashToken()` (sha256, deliberately unsalted — reasoned
inline as unnecessary given the token's own entropy), `issueToken()` (staff-gated, default 14-day
TTL, supersedes prior active token, retries once on a `23505` unique-violation race),
`resolveValidToken()` (hash-and-lookup, checks `status` and `expires_at` at read time — no cron
flip), every outcome collapsed to a generic `{ error: 'link_unavailable' }` so a recipient can't
distinguish wrong-token from revoked from expired (the granular reason is logged server-side only).
**No rate limiting exists anywhere in this module** (confirmed by grep — the only "rate limit" hit
in the whole repo is an unrelated Supabase-auth comment in `app/login/login-form.tsx:27`). Every
resolution attempt (success or denied) writes one `client_access_log` row, gated first by
`isClientPortalEnabled()`.

**Decision presented, not made**: this system is purpose-built for the client portal's
document-review/upload flow (an application-scoped, staff-issued, single-recipient bearer link) and
is the *only* account-free customer-facing access mechanism in the repo today. It is a strong
structural match for a quote/invoice link — same shape (staff or system issues a scoped, expiring,
revocable, hashed bearer token; recipient opens a document without an account). Genuine differences
worth resolving explicitly before reuse, not silently worked around:

1. **Scoping is `application_id`-shaped.** A quote/invoice belongs to a `projects`/`clients` pair
   that may have no `permit_applications` row at all (the master prompt is explicit that a permit is
   optional). Reusing this table as-is would require either (a) making `application_id` nullable and
   adding a `project_id`/`quote_id`/`invoice_id` pointer alongside it, or (b) a parallel table in the
   same project 2 schema with the identical pattern but scoped to the financial-document ID instead.
   Both are "extend," not "reuse verbatim."
2. **No rate limiting today** is an acceptable-so-far gap for a low-traffic internal document
   review flow; a customer-facing *payment* link is a materially different risk profile (the master
   prompt explicitly requires rate-limiting the public token-resolution endpoint for this module).
   That work does not exist yet regardless of which token table backs it.
3. **The token confirms identity/possession of a link, not payment authorization.** The master
   prompt requires an explicit POST confirmation before accepting a quote or triggering payment, and
   says a GET/preview-bot/email-scanner must never trigger either — this is not yet a solved problem
   anywhere in the codebase (the existing system's actions, e.g. document upload, are themselves
   already POST-gated per `lib/bridge/client-portal.ts:970-980`'s call site, which is a good sign the
   convention is already followed elsewhere, but "accept a quote" and "make a payment" are new,
   higher-stakes action types that need their own explicit confirmation step design).

Recommendation surfaced for owner decision (§I, blocking question 3): **extend** the existing
project-2 schema and `lib/bridge/client-portal.ts` gateway pattern (new token-purpose column or a
sibling table following the identical shape) rather than building a third, independent bearer-token
system — but do not treat this as authorized; it is a recommendation pending the explicit decision
the master prompt requires before any implementation.

## §5. Background jobs, reminders, and email

Inngest is the only queue; there is no outbox table (§1). Functions today:
`lib/inngest/functions/{extract,audit,generate-pdf}.ts`, registered in
`app/api/inngest/route.ts:1-14`. The master prompt's requirement that reminders "never depend on
request-lifetime timers" and instead use "a durable database outbox and documented scheduler/worker
entry point" if a durable queue is absent does not strictly apply — Inngest itself is that durable
mechanism (steps memoize on retry, confirmed by a comment in `lib/inngest/functions/audit.ts:153-164`
explaining exactly why a combined step was split to avoid duplicate-insert-on-retry). A recurring
reminder (e.g. "invoice due in 3 days") needs Inngest's scheduled/cron trigger capability or a
`step.sleepUntil()` pattern — neither currently has a precedent in this repo to cite; this would be
new territory, not a reuse of an existing pattern, and should be treated as such in planning.

**Email**: **not present on `main` today.** A full email-sending capability (`lib/email/resend-client.ts`,
provider: Resend, function `sendFailureEmail()`, lazy client construction so import never throws
when unconfigured, `RESEND_API_KEY`/`RESEND_FROM_ADDRESS` env vars) exists only on the still-open,
unmerged `feat/failure-notifications` branch (PR #15). Its "live sending off by default" pattern —
`isFailureNotificationsEnabled()` checked as the literal first line of the handler, returning
immediately with zero DB/network work when off, rather than sending a mocked/logged email — is
exactly the master prompt's "keep live sending off by default, use mocks where configuration is
missing" requirement, demonstrated end-to-end, and is a good template to follow once (if) that PR
merges. **This module cannot assume an email-sending capability exists on `main` yet**; if Phase A
implementation starts before PR #15 merges, either wait for it, or this module's own email need
becomes the first real user of a `lib/email/` module and should be built to the same standard (lazy
client, non-throwing send, explicit off-by-default flag) rather than duplicating it under a
different shape.

## §7. Suggested integration shape (plan, not authorization)

Following the master prompt's own instructions and this repo's `features/` convention precedent
(none currently exists under that exact name — this would be the first — but the module-isolation
intent matches how `lib/billing/`, `lib/entitlements/`, and `lib/bridge/client-portal.ts` are already
kept as narrow, single-purpose seams with header comments stating their own boundaries):

- `features/quotes-payments/{components,domain,services,validation,adapters,tests}` — domain
  calculations (money/tax engine, invariant checks) kept framework-free per the master prompt,
  testable without React or a live Supabase client the same way `lib/entitlements/index.test.ts`
  proves `resolveEffectiveTier()` is DB-free-testable (that file's own header states "no vitest test
  file anywhere in this codebase mocks Supabase" — this module's domain-layer tests should hold to
  the same discipline).
- New tables (org-scoped, additive migrations only, next number after whatever is on `main` at
  implementation time — 43 as of this pass, but note PR #17 adds a 44th that may or may not have
  merged by the time this module starts): a billing/tax profile on `organizations` (or a new
  1:1 table, following `org_subscriptions`'s own 1-row-per-org pattern), `estimates` (+ versioned
  line items), `estimate_acceptances`, `invoices` (+ line items, immutable issue snapshot per the
  master prompt's requirement), `change_orders` (Phase B), `payments` + `payment_allocations`,
  `credit_notes`, `tax_rule_versions` + `tax_decisions`, plus whatever the §4 token decision
  produces. All tenant-qualified FKs, indexes on `org_id`/`project_id`/`status`/`due_date`, no
  cascading delete of issued financial history — mirroring `application_documents`'s own
  "no hard DELETE, archive/revision instead" precedent (§2.5).
- Server-side authorization: RLS is the enforcement layer that actually matters today (§2.2) — a
  Quotes & Payments authorization design should not assume `lib/authz/index.ts`'s `can()` is
  enforced anywhere unless this module either (a) becomes the first real consumer that wires it in,
  or (b) follows the RLS-first pattern every other table in this repo actually uses. This is a real
  design decision the master prompt implicitly requires ("map roles to the actual repository role
  enum and authorization matrix") but the repo currently has two matrices (the SQL role enum via RLS,
  and the unused TS `can()` table) that don't obviously agree — see §I blocking question 2.
- SQL test files following §3.4's exact pattern, one province-tax fixture set per AB/ON/BC as the
  master prompt's §8 requires, wired automatically into the existing `npm run test:sql` CI job.

This is a plan sketch for review, not a sub-phase table with token-ready sign-off lines — the master
prompt's own phase/sub-phase approval structure (Phase A, then A.1/A.2/... as the owner chooses to
gate them) should be authored as its own follow-up once §I's blocking questions are answered, the
same way `GATE_2_0_SPEC.md` was written only after `GATE_2_0_FINDINGS.md` settled its own open
questions.

## §9. Risks (found, not yet mitigated)

1. **No rate limiting anywhere in the existing token-resolution path** (§4) — directly relevant
   since this module's public links are higher-stakes (payment, not just document view) than the
   existing client-portal use case that pattern was built for.
2. **Two disagreeing authorization matrices** (§2.2) — the SQL `org_role` enum actually enforced via
   RLS, and the unused TS `can()` role/action/resource matrix — create a real risk of this module's
   design documentation citing the wrong one as "the" authorization source.
3. **Email capability doesn't exist on `main` yet** (§5) — a Phase A dependency (quote/invoice
   delivery, reminders) currently only exists on an unmerged branch; timeline risk if this module
   starts before that PR lands.
4. **`application_id`-shaped token scoping** (§4) doesn't fit a permit-less job cleanly without
   schema change — a naive reuse would either force a fake `application_id` or silently assume every
   quote has a permit application, both wrong per the master prompt's explicit "permit is optional"
   rule.
5. **BC PST classification risk is a business/legal risk this codebase cannot resolve alone** — the
   master prompt is explicit that mixed/ambiguous cases must route to `REVIEW_REQUIRED`; no existing
   code in this repo does tax-category classification today (§2.6 confirms zero prior art), so this
   is entirely new, high-consequence logic with no existing pattern to lean on beyond the
   float-free-money discipline in `lib/money/cents.ts`.
6. **Storage bucket path convention is application-scoped** (§2.5) — reusing it for
   quote/invoice PDFs either requires a new bucket or a path-convention change; get this wrong and
   RLS policies silently don't cover the new documents.
